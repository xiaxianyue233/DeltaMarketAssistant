# 开发过程记录

本文根据本次工程已有开发对话、现存代码和测试记录整理。省略账号标识、完整游戏截图、个人路径和原始对话，不把对话中的设想当作已经验证的游戏机制。

## 最初目标

用户将目标商品加入收藏，队首通常最接近开放时间。工具在一级允许进入购买后打开二层，按时提交，再处理结果、返回、刷新和下一件。实现采用 C# / .NET 8 / WinForms，本地截图识别，不引入游戏进程注入或云端识图。

## 问题如何推动设计

| 观察到的问题 | 最终采用的处理方式 |
| --- | --- |
| 只识别到按钮却没有点击 | 明确区分“仅识别”和“自动购买”，每次启动以界面所选模式为准 |
| 高 DPI 下说明文字被截断 | 调整布局、缩放和控件尺寸，加入界面保存及布局检查 |
| 单次点击不能稳定进入请求队列 | 改为有间隔、有截止时间的连续提交，而非一次性堆积输入 |
| 按 Esc 连续退了两个界面 | 原窗口验证、连续帧确认、发送前复核，每轮最多单次 Esc |
| 游戏自动返回后仍在点 | 一级与刷新特征优先停点，检测二层消失并确认一级稳定 |
| 队列满、roll 失败留在二层 | 增加本地结果文字模板，先停点再进入受保护返回流程 |
| 成功后的两段页面无法继续 | 单次跳过后验证新的继续页面，再单次空格，最后确认一级 |
| 参数修改后被界面还原 | UI 与后端共用时间定义，整体校验后保存，运行时使用独立快照 |
| 下一件只剩很短倒计时 | 分开一级开窗与二层冲刺，去掉不必要的返回/刷新等待，引入本地数字模板 |
| 零秒附近交接似乎停点 | v1.19 锁定单轮点击结束时点，临时数字失配不重新等待 |
| 打开下一件时只显示“2天23小时” | v1.18 先受保护返回；经用户进一步要求，v1.20 改为验证绿色按钮后最多两秒补购 |

这些迭代没有证明请求越多就一定能提高成交概率。工具能控制本地提交节奏，无法确认服务端接受了哪些请求，也无法保证相邻商品全部赶上。

## v1.20 验证结果与边界

- 当时完整本地测试记录为 30 项通过，包含个人截图与校准配置驱动的扩展测试。
- 覆盖 720p、1080p、1440p、4K 的挂牌识别、原二层验证和返回条件。
- 补购测试覆盖两帧触发、灰色按钮拒绝、两秒截止、不同点击间隔、不重复延长、停止后不重启、正常冲刺不追加补购。
- 测试不等同于真实购买，也不证明线上响应、游戏规则或反自动化策略不变。
- 仓库保存代码、局部模板、局部数字样本和测试；个人全屏截图与配置留在本机，测试复现方式见 [TESTING.md](TESTING.md)。

旧开发目录包含多个历史 EXE 发布目录，但没有旧版 Git 提交。现在将当前源码作为 v1.20.0 的真实基线，把之前的变化保存为本文和 [CHANGELOG.md](../CHANGELOG.md)。不反编译旧 EXE 冒充原始源码，不为没有源码快照的版本建立误导性标签。
